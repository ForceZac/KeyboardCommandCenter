# TRD: Rust Native Module for Active Window Detection

**Task:** TASK-0009
**Branch:** goals/9-rust-native-module
**PRD:** research/agents/prds/goal-04-process-detection.md
**Date:** 2026-05-09

---

## What we're building

The PRD requires a low-overhead native module that returns the foreground application's process name, window title, and macOS bundle ID. This task delivers that module as a Rust crate compiled via `napi-rs` into a platform-specific `.node` binary. A TypeScript wrapper in `packages/desktop/src/platform/` loads the binary and exports a typed `getActiveWindow()` function for the main process. Platform adapters for Win32 (Windows) and NSWorkspace (macOS) are isolated behind a Rust trait so the strategy pattern is enforced at compile time via `#[cfg(target_os)]`. The polling frequency, IPC channel, and settings toggle are intentionally out of scope — those land in TASK-0010.

---

## Technical components needed

**New Rust crate (`packages/desktop/native/`):**
- `Cargo.toml` — declares `cdylib` crate type, napi-rs deps, and per-platform feature flags; this is the napi-rs build entry
- `src/lib.rs` — registers the `get_active_window()` `#[napi]` function; calls the platform dispatch layer and converts to a napi-rs return type
- `src/platform/mod.rs` — defines `ActiveWindowInfo { process_name, window_title, bundle_id? }` struct and dispatches to the platform adapter via `#[cfg(target_os)]`
- `src/platform/macos.rs` — macOS adapter using `objc2` + `objc2-app-kit`; reads `NSWorkspace.shared.frontmostApplication` for process name, window title, and bundle identifier; compile-guarded to macOS only
- `src/platform/windows.rs` — Windows adapter using `windows-rs`; calls `GetForegroundWindow → GetWindowThreadProcessId → OpenProcess → GetModuleFileNameExW` for process exe path, `GetWindowTextW` for title; compile-guarded to Windows only
- `build.rs` — napi-build setup needed to emit TypeScript type definitions during `cargo build`

**New TypeScript platform wrapper (`packages/desktop/src/platform/active-window.ts`):**
- Loads the compiled `.node` binary via `require()` at runtime
- Wraps load in try/catch — returns null without crashing Electron if the binary is absent or fails to load (e.g. wrong architecture, missing on the current platform in dev)
- Exports `ActiveWindowInfo` interface and `getActiveWindow(): ActiveWindowInfo | null`
- This is the only file the rest of the Electron main process imports — the Rust crate is never imported directly

**Modified `packages/desktop/package.json`:**
- Add a `build:native` script (`napi build --platform --release --js false`) for compiling the Rust crate
- Add `napi` and `@napi-rs/cli` as dev dependencies
- Add a `postinstall` hook or `prepare` script to auto-build the native module after `npm install`

**Modified `packages/desktop/forge.config.js`:**
- Add the compiled `.node` binary path to `packagerConfig.extraResources` (or `asar` unpack glob) so Electron Forge bundles it correctly in the packaged app

**Generated TypeScript types (`packages/desktop/native/index.d.ts`):**
- Auto-generated by `napi build --dts` from Rust type annotations; committed to repo
- Allows TypeScript to type-check imports of `getActiveWindow()` even without the compiled binary

**Schema changes:** None

**API changes:** No new REST endpoints. `getActiveWindow()` is a synchronous in-process call within the Electron main process.

## Key architectural decisions

- **napi-rs over neon:** napi-rs has better TypeScript type generation via `#[napi]` macros, active maintenance, and is the current community default for new Electron native modules. Neon requires more manual type definition work.

- **Strategy pattern in Rust, not TypeScript:** Platform dispatch (`#[cfg(target_os = "macos")]` / `#[cfg(target_os = "windows")]`) happens at Rust compile time rather than at TypeScript runtime. This avoids shipping dead platform code and makes the adapter boundary explicit.

- **Synchronous call, not async:** `getActiveWindow()` is synchronous. The window title and process name are available without async OS APIs. Keeping it sync simplifies the calling code in TASK-0010's polling loop. If a platform call takes >1ms (unexpected), the polling service can add its own debounce.

- **Graceful null, not thrown exception:** If the `.node` binary is absent (e.g. `npm install` ran but `napi build` didn't run yet), the TypeScript wrapper returns null rather than crashing. This lets the app start in dev mode even without a compiled binary.

- **Committed generated `.d.ts`:** The napi-rs type definitions are committed to the repo. This allows TypeScript compilation and IDE autocompletion without requiring the native build step, which simplifies CI and onboarding.

- **No Linux support:** PRD explicitly defers Linux to Goal 10. No Linux `#[cfg]` branches are written now.

## Test coverage plan

- **Vitest unit tests (`packages/desktop/src/platform/active-window.test.ts`):**
  - Graceful null when the `.node` binary cannot be loaded (mocked require failure)
  - Returns a valid `ActiveWindowInfo`-shaped object when the native module loads and returns data
  - `processName` is always a non-empty string when detection succeeds
  - `bundleId` is undefined on non-macOS platforms (not required)

- **Manual smoke test (not automated):**
  - Start app with `electron-forge start`, observe that main process logs `getActiveWindow()` result without uncaught exceptions
  - Switch to a different app, call again, confirm different processName

- **Platform-specific CI tests are out of scope for this task** — automated integration requires platform runners (Windows/macOS) that are not yet wired up (that's Goal 9 — CI/CD). The Vitest suite covers the load/fallback logic only.

## Risks and open questions

- **Rust toolchain availability:** The napi-rs build requires `rustup` and the correct target triple. Developers without Rust installed will hit a build failure on `npm install`. Mitigation: add a clear error message in the `postinstall` script and document the requirement.

- **Electron ABI compatibility:** The `.node` binary must match the Node.js ABI bundled with the Electron version (`electron@^28.0.0` uses Node 18.x). `napi-rs` targets the N-API stable ABI which is forward-compatible across Node versions, so this should be fine — but the Electron major version should be locked in devDependencies.

- **webpack bundling of `.node` files:** The existing `webpack.main.config.js` already includes `node-loader` for `*.node` files. This handles `require()` during Electron Forge start. For the packaged app (`npm run make`), the `.node` binary must be in `extraResources` so it's accessible outside the ASAR archive. If this is misconfigured, the packaged app will fail to load the native module — the TypeScript wrapper's try/catch prevents a crash, but detection will silently return null.

- **macOS window title:** `NSWorkspace.shared.frontmostApplication.localizedName` gives the app display name, not the window title. True window title requires Accessibility API (`AXUIElement`). PRD says process name is sufficient and window title is nice-to-have — so the macOS adapter returns `localizedName` as `window_title` for now, which is good enough for the mapping layer.

- **TASK-0007 dependency:** This branch is created from `main` before TASK-0007's branch (`goals/7-settings-persistence`) is merged. The native module code is independent of `electron-store` and does not call any TASK-0007 APIs. Merge conflicts are not anticipated. If TASK-0007 merges during this branch's lifetime, a rebase before final PR review will be straightforward.

## Goal

Build a `napi-rs` Rust native module in `packages/desktop/native/` that exposes `getActiveWindow()` returning `{ processName, windowTitle, bundleId? }`. Wire the module into the Electron Forge webpack build so it loads in the main process without manual steps. Platform adapters for Win32 (Windows) and NSWorkspace (macOS) behind a strategy interface. TypeScript types generated by napi-rs. No polling, no IPC — those land in TASK-0010.

## Work breakdown

### Slice 1 — napi-rs project scaffold
- Create `packages/desktop/native/Cargo.toml` — crate-type `cdylib`, napi-rs deps, feature flags per platform
- Create `packages/desktop/native/build.rs` — napi-build setup for generating TypeScript type definitions
- Create `packages/desktop/native/src/lib.rs` — stub that registers an `#[napi]` function `get_active_window()` returning null
- Verify `cargo build` completes (cross-compilation stubs are fine — actual platform code comes next)

### Slice 2 — Platform adapter interface
- Create `src/platform/mod.rs`:
  - `ActiveWindowInfo` struct with `process_name`, `window_title`, `bundle_id` (Option<String>)
  - `get_active_window_info()` function that dispatches to the platform-specific adapter via `#[cfg(target_os)]`
- Update `lib.rs` to call `get_active_window_info()` and convert to napi-rs return type

### Slice 3 — macOS adapter (`src/platform/macos.rs`)
- Use `objc2` and `objc2-app-kit` crates to call `NSWorkspace.shared.frontmostApplication`
- Extract `localizedName` → window_title, `bundleIdentifier` → bundle_id, `executableURL.lastPathComponent` → process_name
- Compile-guard the entire file with `#[cfg(target_os = "macos")]`
- Graceful degradation: return partial struct if any field unavailable (bundle_id is optional)

### Slice 4 — Windows adapter (`src/platform/windows.rs`)
- Use `windows-rs` crate (`windows` feature: `Win32_UI_WindowsAndMessaging`, `Win32_System_Threading`, `Win32_Foundation`)
- Call `GetForegroundWindow()` → `GetWindowThreadProcessId()` → `OpenProcess()` → `GetModuleFileNameExW()` to get exe path
- Call `GetWindowTextW()` for window title
- Extract process name as last path component of exe path, strip `.exe` suffix for normalization
- Compile-guard the entire file with `#[cfg(target_os = "windows")]`
- Graceful degradation: return null from the napi function if any Win32 call fails

### Slice 5 — Electron Forge build integration
- Add `@electron-forge/plugin-local-electron` is NOT needed — use existing webpack plugin
- Add a `postinstall` or `build` hook to `packages/desktop/package.json`: `napi build --platform --release --js false` to compile the Rust crate and emit the `.node` file
- Confirm `node-loader` in `webpack.main.config.js` already handles `*.node` files (it does — verified in existing config)
- Add the compiled `.node` path to `packagerConfig.extraResources` in `forge.config.js` so it's bundled in the Electron app package

### Slice 6 — TypeScript wrapper (`src/platform/active-window.ts`)
- `require()` the native `.node` file (path resolved via `__dirname` relative to webpack output)
- Wrap in a try/catch — if loading fails, export a stub that returns null
- Re-export `ActiveWindowInfo` interface (matches the napi-rs generated types)
- Export `getActiveWindow(): ActiveWindowInfo | null`

### Slice 7 — Tests
- Vitest unit tests for the TypeScript wrapper:
  - When native module loads successfully: `getActiveWindow()` returns an object with `processName` (non-empty string) or null
  - When native module fails to load: `getActiveWindow()` returns null (not throws)
- Manual smoke test: `electron-forge start` loads the app, main process calls `getActiveWindow()` and logs result to console without crashing
- Note: CI platform tests (actually running Win32/macOS detection) are not automated — they require platform-specific hardware. The Vitest suite tests the load/fallback logic only.

## Build notes

- napi-rs requires Rust toolchain. In CI, use `dtolnay/rust-toolchain` action. Locally, developers must have `rustup` installed.
- Cross-compilation is NOT in scope — build on the target platform (Windows binary on Windows, macOS binary on macOS).
- The `.node` binary is platform-specific. `npm run make` on each OS produces the correct binary for that OS.
- `napi-rs` generates TypeScript type definitions automatically via `build.rs` + `napi build --dts`. The generated `.d.ts` is committed to the repo so TypeScript compilation works even without the native binary.
